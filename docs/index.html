MCP와 AI Agent 개념 정리

MCP, AI Agent, Tool Calling, Workflow가 각각 무엇이며 서로 어떻게 연결되는지 백엔드 개발 관점에서 단계적으로 정리한 문서입니다.

MCP = AI가 외부 시스템을 사용하는 방법을 표준화한 프로토콜

AI Agent = 목표를 받고, LLM이 필요한 행동을 선택하며 작업을 반복하는 시스템

핵심 = MCP와 Agent는 같은 기술이 아니며, Agent가 MCP를 사용할 수 있습니다.

목차
  1. 먼저 AI Agent부터
  2. Agent가 되면 차이가 생깁니다
  3. 그러면 MCP는 무엇인가

  5. MCP Server에는 AI가 없어도 됩니다
  6. MCP에는 Tool만 있는 것도 아닙니다
  7. 이제 MCP와 Agent를 합쳐보겠습니다
  8. REST API에 비유하면 더 쉽습니다
  9. 가장 많이 헷갈리는 네 가지
  10. Chatbot / Workflow / Agent / MCP 비교

1. 먼저 AI Agent부터

일반적인 LLM 사용은 단순합니다.

사용자
  │
  ▼
LLM
  │
  ▼
답변

예를 들어:

나: PostgreSQL의 인덱스 종류 설명해줘
LLM: B-tree, Hash, GIN...

LLM이 자신의 지식과 입력된 Context를 바탕으로 텍스트를 생성합니다.

Tool을 붙이면

LLM 밖에 실제 기능을 추가할 수 있습니다.

사용자
  │
  ▼
LLM
  │
  ├─ getWeather()
  ├─ searchDatabase()
  └─ sendEmail()

사용자가:

서울 날씨 알려줘

라고 했다고 가정하겠습니다.

LLM이 직접 날씨를 알고 있는 것이 아니라:

사용자
  │
  ▼
LLM

"현재 날씨 정보가 필요하다"
  │
  ▼
getWeather("Seoul")
  │
  ▼
25°C, Rain
  │
  ▼
LLM
  │
  ▼
"현재 서울은 25°C이고 비가 옵니다."

이게 Tool Calling입니다.

여기까지는 아직 반드시 Agent라고 볼 필요는 없습니다.

2. Agent가 되면 차이가 생깁니다

사용자가 이런 목표를 줬다고 해보겠습니다.

우리 API가 느려진 원인을 찾아줘.

단순 LLM은 실제 서버 상태를 모릅니다.

그런데 Agent에게 Tool들이 있다고 해보겠습니다.

getApplicationLogs()
getContainerStatus()
getSlowQueries()
getRecentDeployments()
explainQuery()

Agent는 한 번 호출하고 끝나는 게 아니라 작업 결과를 보고 다음 행동을 결정합니다. 

목표
"API 지연 원인을 찾아라"
        │
        ▼
       LLM
        │
        │ getApplicationLogs 선택
        ▼
Application Logs
        │
        ▼
       LLM
        │
        │ DB timeout 발견
        │
        │ getSlowQueries 선택
        ▼
Slow Queries
        │
        ▼
       LLM
        │
        │ 특정 SQL 발견
        │
        │ explainQuery 선택
        ▼
EXPLAIN 결과
        │
        ▼
       LLM
        │
        ▼
최종 판단

이게 Agent를 이해하는 핵심입니다.

OpenAI Agents SDK의 실제 Runner도 이런 루프로 정의되어 있습니다. 모델을 호출한 뒤 결과가 최종 답변이면 종료하고, Tool Call이면 Tool을 실행하여 결과를 다시 모델에 전달하며, Handoff이면 다른 Agent로 제어를 넘기는 방식입니다. (OpenAI Agents SDK — Running agents)

Anthropic도 Agent를 LLM이 자신의 프로세스와 Tool 사용을 동적으로 결정하며 목표를 수행하는 시스템으로 구분합니다. 미리 정해진 코드 경로를 따르는 Workflow와 Agent를 구분하는 기준도 여기에 있습니다. (Anthropic — Building effective agents)

그래서 Agent를 가장 단순화하면:

생각
 ↓
행동
 ↓
관찰
 ↓
다시 판단
 ↓
행동
 ↓
...
 ↓
목표 달성

입니다.

3. 그러면 MCP는 무엇인가

여기서 전혀 다른 문제가 하나 생깁니다.

Agent에게 Tool을 어떻게 제공할까요?

직접 코드를 작성할 수도 있습니다.

const tools = {
  getLogs,
  getSlowQueries,
  getContainerStatus,
};

이 Agent에서는 사용할 수 있습니다.

그런데 다른 AI 프로그램에서도 이 Tool을 사용하고 싶으면 또 연결해야 합니다.

내 Agent ───────── PostgreSQL 코드

Claude ────────── PostgreSQL 코드

VS Code ───────── PostgreSQL 코드

다른 Agent ────── PostgreSQL 코드

각 AI Application마다 통합 방법이 달라지는 문제가 생깁니다.

여기서 MCP가 등장합니다.

MCP 공식 문서는 MCP를 AI 애플리케이션을 외부 시스템에 연결하기 위한 오픈 표준으로 정의합니다. 데이터 소스, Tool, Workflow 등을 표준화된 방식으로 AI 애플리케이션에 제공하는 것이 목적입니다. 공식 문서에서는 이를 AI 애플리케이션을 위한 USB-C에 비유합니다. (Model Context Protocol — Introduction)

4. MCP Server

PostgreSQL을 다루는 MCP Server를 하나 만들었다고 생각해보겠습니다.

PostgreSQL MCP Server

이 서버가 이런 기능을 제공합니다.

Tools

get_tables
get_table_schema
execute_readonly_query
explain_query

이제 AI 쪽에서는 PostgreSQL 내부 구현을 직접 알 필요가 없습니다.

              ┌──────────── Claude
              │
              ├──────────── VS Code
              │
PostgreSQL MCP Server
              │
              ├──────────── ChatGPT
              │
              └──────────── 내 Agent

각 프로그램은 MCP라는 동일한 규격을 사용해서 기능을 발견하고 호출할 수 있습니다.

현재 공식 MCP 아키텍처도 이를 Host / Client / Server 구조로 정의합니다. MCP Host가 하나 이상의 MCP Client를 가지고 각각 MCP Server와 통신합니다. MCP 자체는 LLM 사용 방법이나 Agent 실행 방식을 규정하지 않습니다. (Model Context Protocol — Architecture)

5. 중요한 부분: MCP Server에는 AI가 없어도 됩니다

이 부분에서 많이 헷갈립니다.

예를 들어:

PostgreSQL MCP Server

라고 해서 내부에 GPT나 Claude가 들어가는 게 아닙니다.

그냥 프로그램일 수 있습니다.

MCP Server

tools/list
tools/call

        │

PostgreSQL Driver

        │

PostgreSQL

역할은:

"나는 이런 Tool들을 제공한다."

"execute_readonly_query를 호출하면
PostgreSQL에 쿼리하고 결과를 반환한다."

입니다.

판단하는 것은 MCP Server가 아닙니다.

판단은 LLM 또는 Agent가 합니다.

MCP 공식 문서에서도 MCP의 범위는 context exchange protocol에 한정되며, AI 애플리케이션이 LLM을 어떻게 사용하거나 Context를 어떻게 관리할지는 규정하지 않는다고 명시합니다. (Model Context Protocol — Architecture)

6. MCP에는 Tool만 있는 것도 아닙니다

핵심 요소를 단순화하면 이렇게 볼 수 있습니다.

MCP 기능 의미 백엔드식으로 생각하면
Tools 실행 가능한 기능 API / Function
Resources AI에게 제공할 데이터 조회 가능한 데이터
Prompts 재사용 가능한 Prompt Template

예를 들어 Database MCP라면:

Resources

db://schema/users
db://schema/orders

처럼 Schema 정보를 제공할 수 있고,

Tools

execute_query
explain_query

처럼 실제 작업도 제공할 수 있습니다.

MCP 공식 명세도 서버 기능을 Resources, Prompts, Tools 등의 primitive로 정의하고 있습니다. (Model Context Protocol — Architecture)

7. 이제 MCP와 Agent를 합쳐보겠습니다

여기가 가장 중요합니다.

사용자
  │
  │ "API가 느려진 원인을 찾아줘"
  ▼
AI Agent
  │
  │ 판단
  │
  ├───────────────┐
  │               │
  ▼               ▼
Docker MCP     Database MCP
  │               │
get_logs       get_slow_queries
status         explain_query
  │               │
  ▼               ▼
Docker        PostgreSQL

Agent 입장에서는:

Docker를 어떻게 제어하지?
PostgreSQL Driver가 뭔데?
Docker API가 뭔데?

를 신경 쓸 필요가 없습니다.

MCP Server가 제공하는 Tool만 봅니다.

get_logs
get_container_status
get_slow_queries
explain_query

그리고 Agent가 판단합니다.

1. 로그를 확인해야겠다.
2. DB timeout이 있네.
3. Slow Query를 확인해야겠다.
4. SQL 하나가 이상하다.
5. EXPLAIN을 확인해야겠다.
6. Seq Scan이 발생하고 있네.
7. 최종 원인을 보고해야겠다.

그래서 역할을 완전히 분리할 수 있습니다.

Agent
=
무엇을 할 것인가 결정


MCP
=
그 일을 어떻게 외부 시스템에 요청할 것인가


MCP Server
=
실제 외부 시스템과 연결

8. REST API에 비유하면 더 쉽습니다

백엔드 개발 관점에서는 이 비유가 꽤 정확합니다.

일반 웹에서는:

Frontend

   ↓ HTTP

REST API

   ↓

Database

Agent 환경에서는:

AI Agent

   ↓ MCP

MCP Server

   ↓

Database / GitHub / Docker / Slack / Files ...

물론 MCP = REST라고 동일시하면 안 됩니다.

REST는 웹 API 아키텍처 스타일이고 MCP는 AI 애플리케이션과 외부 시스템 사이의 Context/Tool 상호작용을 정의하는 프로토콜입니다.

다만 처음 구조를 이해할 때는:

AI 세계에서 외부 기능을 표준 인터페이스로 노출한다

정도로 잡으면 됩니다. MCP 공식 문서 역시 현재 서버가 AI Action용 Tools, Context Data용 Resources, Interaction Template용 Prompts를 제공하는 Client-Server 구조로 설명합니다. (Model Context Protocol — Architecture)

9. 가장 많이 헷갈리는 네 가지

Tool Calling ≠ MCP

LLM
 ↓
JavaScript function

이것도 Tool Calling입니다.

MCP 필요 없습니다.

MCP를 쓰면:

LLM / Agent
 ↓
MCP Client
 ↓
MCP Server
 ↓
function

이 됩니다.

MCP ≠ Agent

MCP Server

자체는 판단하지 않아도 됩니다.

단순히:

Tool 등록
요청 수신
Tool 실행
결과 반환

만 할 수 있습니다.

Tool Calling ≠ 반드시 Agent

사용자
 ↓
LLM
 ↓
Tool 한 번 호출
 ↓
답변

만으로도 Tool Calling은 가능합니다.

Agent의 핵심은 보다 일반적으로:

목표
 ↓
판단
 ↓
행동
 ↓
결과 관찰
 ↓
다시 판단

이라는 동적인 실행 루프에 있습니다. OpenAI Agents SDK의 공식 Agent Loop도 이 방식으로 구현되어 있습니다. (OpenAI Agents SDK — Running agents)

Multi-Agent ≠ Agent의 필수 조건

Agent 하나만 있어도 됩니다.

User
 ↓
Agent
 ├─ Tool A
 ├─ Tool B
 └─ Tool C

여러 Agent가 필요한 경우에만:

Manager Agent
   │
   ├─ DB Agent
   ├─ Docker Agent
   └─ Git Agent

처럼 확장합니다.

OpenAI Agents SDK에서는 이를 Handoff 또는 Agent-as-Tool 등의 orchestration 방식으로 지원하지만, Agent의 필수 구성 요소는 아닙니다. (OpenAI Agents SDK — Handoffs)

10. Chatbot / Workflow / Agent / MCP를 한 번에 비교

이 표만 확실하게 이해하셔도 개념이 상당 부분 정리됩니다.

개념 역할
LLM 입력을 받아 추론하고 출력 생성
Chatbot LLM과 사용자가 대화할 수 있는 애플리케이션
Tool Calling LLM이 외부 함수를 호출
Workflow 개발자가 정해놓은 순서대로 LLM/Tool 실행
Agent LLM이 상황에 따라 다음 행동과 Tool을 선택
MCP AI 애플리케이션과 외부 Tool/Data 연결 방식 표준화
MCP Server MCP 규격으로 Tool/Data를 외부에 제공

Workflow와 Agent 차이가 특히 중요합니다. Anthropic의 공식 구분에서도 Workflow는 코드가 미리 정의한 경로로 LLM과 Tool을 오케스트레이션하는 시스템이고, Agent는 LLM이 Tool 사용과 실행 과정을 동적으로 결정하는 시스템입니다. (Anthropic — Building effective agents)

11. 코드로 보면 더 명확합니다

일반 Workflow

개발자가 순서를 정합니다.

const logs = await getLogs();
const queries = await getSlowQueries();
const explanation = await llm.analyze(logs, queries);

return explanation;

LLM은:

getLogs 할까?
getSlowQueries 할까?

를 결정하지 않습니다.

코드가 결정합니다.

Agent

Available Tools

- getLogs
- getSlowQueries
- explainQuery
- getDeployments

만 제공해놓고:

API가 느려진 원인을 조사해라.

라는 Goal을 줍니다.

이제 LLM이:

getLogs부터 호출
        ↓
결과 판단
        ↓
getSlowQueries 호출
        ↓
결과 판단
        ↓
explainQuery 호출
        ↓
최종 답변

을 결정합니다.

이 제어권의 일부가 코드에서 LLM으로 이동했다는 것이 Agent를 이해하는 가장 중요한 포인트입니다. Anthropic도 최근 Agent 설명에서 사람은 무엇을 달성할지를 정하고 Agent가 어떻게 달성할지를 결정하는 구조로 설명하고 있습니다. (Anthropic — Claude Code expertise)

12. MCP를 코드 관점으로 바꾸면

기존에는 Agent 프로젝트 내부에:

src/
 └─ tools/
     ├─ database.ts
     ├─ docker.ts
     └─ github.ts

가 있을 수 있습니다.

MCP로 분리하면:

database-mcp-server
 └─ Tools
     ├─ query
     └─ explain


docker-mcp-server
 └─ Tools
     ├─ logs
     └─ status


AI Agent
 └─ MCP Client

가 됩니다.

그러면 Database MCP Server는 특정 Agent에 종속되지 않습니다.

             ┌─ Agent A
             │
Database MCP ├─ Agent B
             │
             ├─ Claude
             │
             └─ VS Code

이 재사용 가능한 표준 Integration Layer가 MCP의 가치입니다. MCP 공식 문서도 한 번 구축한 MCP Server를 여러 지원 AI Client에 통합할 수 있다는 점을 주요 장점으로 설명합니다. (Model Context Protocol — Introduction)

13. 지금 단계에서는 이렇게 공부하시는 게 가장 낫습니다

처음부터 MCP + Multi-Agent + RAG를 전부 섞으면 개념이 더 꼬입니다.

제가 권하는 순서는:

① LLM
        ↓
② Function / Tool Calling
        ↓
③ Agent Loop
        ↓
④ MCP
        ↓
⑤ Agent + MCP
        ↓
⑥ Guardrail / Human Approval
        ↓
⑦ Multi-Agent

입니다.

특히 ② → ③ → ④를 분리해서 직접 구현해 보면 금방 명확해집니다.

Phase 1
LLM이 직접 만든 Function Tool 호출

Phase 2
LLM이 Tool 결과를 보고
다음 Tool을 결정하는 Agent 구현

Phase 3
기존 Tool을 MCP Server로 분리

Phase 4
Agent가 MCP Client로 MCP Server 사용

이렇게 하면 마지막에는 같은 기능이:

직접 Function Calling
        ↓
Agent Tool
        ↓
MCP Tool

로 어떻게 변하는지 직접 비교할 수 있습니다.

최종적으로 머릿속에 이 구조만 남기시면 됩니다

                 ┌───────────────┐
                 │     User      │
                 └───────┬───────┘
                         │ Goal
                         ▼
                 ┌───────────────┐
                 │   AI Agent    │
                 │               │
                 │ LLM + Loop    │
                 │               │
                 │ "무엇을 할지" │
                 │     판단      │
                 └───────┬───────┘
                         │
                        MCP
                         │
           ┌─────────────┼─────────────┐
           ▼             ▼             ▼
      ┌─────────┐   ┌─────────┐   ┌─────────┐
      │ DB MCP  │   │Git MCP  │   │Docker   │
      │ Server  │   │ Server  │   │MCP      │
      └────┬────┘   └────┬────┘   └────┬────┘
           │             │             │
           ▼             ▼             ▼
      PostgreSQL       GitHub        Docker

Agent는 판단합니다.

Tool은 행동합니다.

MCP는 Agent/AI와 Tool 사이의 연결 방법을 표준화합니다.

이 세 문장을 기준으로 잡으시면 됩니다.
