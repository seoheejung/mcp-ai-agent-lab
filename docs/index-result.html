PHASE
01

Tool Calling: LLM에게 사용할 함수를 알려주기

처음에는 Agent가 없습니다. LLM이 질문에 맞는 Function Tool을 한 번 선택하고, 그 결과를 받아 구조화된 진단 보고서를 만듭니다.

이 작업이 무엇이고, 왜 하나요?

LLM이 최신 서비스 상태를 스스로 알 수는 없으므로, FastAPI Backend를 조회하는 세 함수를 선택지로 제공합니다. “무엇을 호출할 수 있는가”와 “호출 결과를 답변에 어떻게 쓰는가”를 가장 작은 단위로 확인하는 단계입니다.

이전 단계와 무엇이 다른가요?

시작 단계입니다. 일반 텍스트 응답과 달리 LLM은 함수 호출을 요청할 수 있지만, 결과를 보고 다음 행동을 반복해서 정하는 Agent Loop는 아직 없습니다.

질문→Responses API→Function Tool→진단 결과

실제 구현 구조

  • Read-only Function Tool: get_service_status, get_recent_metrics, get_recent_logs
  • 각 Tool은 HTTPX로 기존 FastAPI Diagnostics API를 호출합니다.
  • Tool 결과를 function_call_output으로 다시 전달하고 DiagnosticReport로 검증했습니다.

Tool Calling은 Agent와 같은 말이 아닙니다.

여기서는 LLM이 함수 호출을 선택합니다. 하지만 여러 결과를 관찰하며 다음 행동을 계속 결정하는 실행 루프는 아직 없습니다.

PHASE
02

Agent Loop: 누가 호출 순서를 결정할까?

같은 세 Function Tool을 두 방식으로 실행했습니다. Workflow는 코드가 순서를 정하고, Diagnostics Agent는 모델이 다음 Tool을 선택합니다.

이 작업이 무엇이고, 왜 하나요?

“응답이 느린 원인을 조사해줘”라는 하나의 목표에는 상태, 지표, 로그가 모두 필요합니다. 고정 순서와 Agent Loop의 제어권 차이를 실제 요청·토큰·Trace로 비교했습니다.

이전과 달라진 점

Workflow: code decides≠Agent: model chooses next Tool

두 방식 모두 같은 Backend, fixture, 모델, Read Tool을 사용했습니다.

실제 구현 구조

Deterministic Workflow는 get_service_status → get_recent_metrics → get_recent_logs → LLM으로 구현했습니다. Diagnostics Agent에는 세 Tool과 DiagnosticReport 출력 schema를 주되 Tool 순서는 코드로 고정하지 않았습니다.

두 실행 모두 DiagnosticReport를 반환했습니다. Workflow는 recommended_action=restart_service, Agent는 recommended_action=none이었습니다. 실제 Agents SDK Trace도 생성됐고, Workflow에는 function과 generation, Agent에는 response, function, turn, agent, task span이 기록됐습니다.

핵심 개념

Workflow는 정해진 길이고, Agent는 선택 가능한 길입니다.

이번 Agent 실행의 순서도 status → metrics → logs였지만, 그 순서를 코드가 강제한 것은 아닙니다. 이 차이가 Agent Loop입니다.

PHASE
03

MCP Server: 기능을 표준 통로로 따로 제공하기

이번에는 LLM과 Agent를 사용하지 않았습니다. stdio FastMCP Server가 Tool을 제공하고, 독립 FastMCP Client가 발견하고 호출하는지만 검증했습니다.

이 작업이 무엇이고, 왜 하나요?

MCP는 Agent가 아닙니다. MCP는 Client와 Server가 Tool을 발견하고 호출하는 약속입니다. 그래서 Agent 없이도 Server와 Client만으로 기능 제공과 오류 전달을 확인할 수 있습니다.

이전과 달라진 점

독립 MCP Client↔ stdio ↔FastMCP Server→Backend

실행을 판단하는 주체를 추가한 것이 아니라, Tool 연결 인터페이스를 분리했습니다.

실제 구현 구조

FastMCP 3.4.7, stdio transport, 세 Read-only MCP Tool을 사용했습니다. 검증용 Client는 Phase 3의 독립 검증 전용이며 Phase 4 Agent 코드 재사용을 위해 확장하지 않았습니다.

핵심 개념

MCP Server는 “판단자”가 아니라 “제공자”입니다.

Server는 어떤 Tool이 있는지 알리고, 요청을 받아 실행하고, 결과나 오류를 돌려줍니다. LLM 또는 Agent는 이 단계에 없어도 됩니다.

PHASE
04

Agent + MCP: Agent는 그대로, 연결만 바꾸기

Diagnostics Agent가 Local Function Tool을 쓸 때와 stdio MCP Tool을 쓸 때를 같은 조건에서 비교했습니다.

이 작업이 무엇이고, 왜 하나요?

“MCP를 붙이면 Agent 자체가 달라지는가?”를 분리해 보기 위한 실험입니다. Agent의 이름, instruction, 출력 schema, 평가 질문, Backend fixture, 모델은 그대로 두고 Tool 연결만 바꿨습니다.

이전과 달라진 점

Diagnostics Agent→Local Function Tools/MCPServerStdio → MCP Tools

Phase 3의 MCP Server를 Agent가 실제 Client로 사용한 첫 단계입니다.

PHASE
05

Human Approval: 상태를 바꾸기 전에 멈추기

Read Tool은 그대로 두고, fixture 상태를 바꾸는 restart_service Write Tool에만 사람의 승인 또는 거절을 적용했습니다.

이 작업이 무엇이고, 왜 하나요?

상태 조회와 상태 변경은 위험도가 다릅니다. 재시작 요청을 모델이 만들었다고 바로 실행하지 않고, Web UI에서 사람이 결정할 때까지 Agent 실행을 중단하는 흐름을 만들었습니다.

이전과 달라진 점

Agent→restart request→PAUSE→Web Approve / Reject→same RunState

Approval 대상은 restart_service 하나뿐입니다. Read Tool에는 적용하지 않았습니다.

실제 구현 구조

FastAPI POST /services/{service}/restart와 FastMCP restart_service를 추가했습니다. 실제 Docker나 서버를 재시작하지 않고 fixture만 degraded → healthy로 바꿉니다. Pending RunState와 MCP stdio 연결은 현재 구현에서 프로세스 메모리에 보관합니다.

두 실험은 degraded fixture로 시작했고, 세 Read Tool 뒤 restart_service({"service":"order-api"}) 승인 요청에서 멈췄습니다. 승인 전에는 restart Tool Call이 없었습니다. Approve 후에는 정확히 한 번 실행되어 healthy가 됐고, Reject 후에는 실행되지 않아 degraded가 유지됐습니다. Agents SDK Trace도 실제 생성됐습니다.

핵심 개념

Approval은 Tool 자체를 없애는 기능이 아니라, 실행 직전에 제어를 사람에게 넘기는 정책입니다.

이 구현에서 읽기 작업은 계속 자동으로 진행됩니다. 오직 Write Tool인 restart_service만 중단·승인·재개 흐름을 거칩니다.

PHASE
06

Multi-Agent: 필요한 역할에게만 필요한 Tool 주기

정확히 두 Agent만 사용했습니다. Diagnostics Agent는 읽고 판단하며, Operations Agent는 Handoff를 받은 뒤 상태 확인과 승인된 재시작만 할 수 있습니다.

이 작업이 무엇이고, 왜 하나요?

모든 Agent에 모든 Tool을 주지 않고 역할별 최소 권한을 적용하는 단계입니다. 진단 담당자는 restart_service를 볼 수 없고, 작업 담당자만 승인 정책이 붙은 Write Tool을 볼 수 있습니다.

이전과 달라진 점

Diagnostics Agent: read only→ HANDOFF →Operations Agent: status + approved restart

구현한 협업 방식은 Handoff뿐입니다. Manager, Agents-as-Tools, 병렬 Agent, Memory, RAG는 추가하지 않았습니다.

실제 구현 구조

  • Diagnostics Agent: get_service_status, get_recent_metrics, get_recent_logs만 노출
  • Operations Agent: get_service_status, restart_service만 노출
  • restart_service는 Phase 5와 같이 always Human Approval을 유지
  • Web은 명시적 Handoff와 자율 판단을 따로 시작하고, Handoff·Tool Call·승인 대기·같은 RunState 재개 결과를 표시

Single Agent와 Multi-Agent 비교에서 주의할 점

같은 Backend, degraded fixture, MCP stdio, 모델 설정, 자율 판단 질문으로 Single Agent도 실제 실행했습니다. Single Agent는 status, metrics, logs를 호출했고 2 LLM requests, 947 input / 571 output / 1,518 total tokens, 13,017.47 ms를 기록했습니다. 하지만 restart approval이 발생하지 않았습니다. 따라서 Multi-Agent의 Reject 경로와 완전히 동일한 실행 경로가 아니며, 이 한 번의 수치로 성능이나 품질의 우열을 결론 내리지 않습니다.

핵심 개념

Multi-Agent의 핵심은 Agent 수가 아니라 책임과 권한의 분리입니다.

이번 Trace에는 실제 handoff span이 있었고, Single Agent Trace에는 없었습니다. Handoff는 진단 결과와 다음 작업의 책임을 다른 Agent로 넘기는 방식입니다.

마지막으로 구분해서 기억하기

Tool Calling은 LLM이 외부 함수를 호출하는 방식입니다. Agent는 그 결과를 보고 다음 행동을 선택하는 실행 루프입니다. MCP는 Tool과 데이터를 Client/Server 방식으로 발견하고 호출하는 표준 통로입니다. Human Approval과 Handoff는 그 실행에 사람의 결정과 역할 경계를 더합니다.

이 설명 페이지의 수치와 결과는 docs/phase1-tool-calling.md부터 docs/phase6-multi-agent.md까지 기록된 실제 실행 결과를 요약한 것입니다. 미측정 값과 성능 우열은 추가하지 않았습니다.
